# 模型选择与替换分析

- 日期：2026-08-13
- 来源：基于《创作流程20260810.txt》现有 5 家模型的实际角色
- 关联：spec §1.1（收敛 1-2 家）、§8.1（降级链）、V-C02（供应商待确认）

---

## 一、现状：5 家模型的角色映射

| 模型 | 角色 | 调用次数/条 | 模式 |
|---|---|---|---|
| 豆包 | ① 正文生成 + ② 搜实景图 | 2 | 快速 + 专家 |
| Kimi | ③④ 两轮校稿 | 2 | 快速 |
| DeepSeek | ⑤ 检查（约束文档改写） | 1 | 快速 |
| workbuddy | ⑥ 检查 + ⑦ 生图提示词 | 2 | hy3 |
| ChatGPT | ⑧ 图片生成（3:4 竖版图文） | 1 | plus 高级 |

**链路结构**：
- 文本链路 = 4 家串行（豆包生成 → Kimi 校稿×2 → DeepSeek 检查 → workbuddy 检查+生图提示词），共 6 次调用
- 图片链路 = 2 家（豆包搜图 → ChatGPT 生成图），共 2 次调用

---

## 二、三个关键发现

### 发现 1：文本链路的 4 家是历史冗余，不是设计

"豆包生成 → Kimi 两轮校稿 → DeepSeek 检查 → workbuddy 检查+生图提示词"是一条生成→校→检→检→再改的串行链。校稿和检查是同一动作的两家实现——这是"多模型交叉质检"的朴素形态，本质是"用不同模型互相挑错，降低单一模型的错误率"。

可收敛为：
- **1 家强文本模型**负责生成 + 自校（如 DeepSeek 或豆包，快且便宜）
- **1 家交叉质检模型**负责校稿 + 检查（如 Kimi，长文本校对能力强）
- **生图提示词**复用生成模型，砍掉 workbuddy 单独生成提示词这一步

即从 4 家 → 2 家文本模型，调用从 6 次 → 3-4 次。

### 发现 2：图片生成是 ChatGPT 独有，无法收敛

ChatGPT（DALL-E）是唯一能稳定产出「3:4 竖版 + 中文黑体 + 融合实景图 + 去水印去人」的。这是 8.1/8.2/8.3 三类提示词反复强调的硬约束：

- "所有文字必须使用标准可读中文黑体风格"（禁止艺术化变形/阴影/描边/透视扭曲）
- "不出现人脸"、"实景图上有水印的必须去掉"
- "每一张图上尽量都要有两个的对比"（对比类专属）

没有等价替代。图片生成是 ChatGPT 一家独占。

### 发现 3："收敛到 1-2 家"与图片现实矛盾

spec §1.1 说"收敛到 1-2 家"，但现实是：

| 类别 | 最少家数 | 说明 |
|---|---|---|
| 图片生成 | 1（ChatGPT） | 独占，无替代 |
| 文本生成+校稿 | 1-2（豆包/DeepSeek/Kimi 选 1-2） | 可收敛 |
| 搜索（实景图） | 1（豆包搜索或换别家） | 搜索 API |
| OCR | 0（PaddleOCR 自建） | 非供应商 |

**实际最少 3 家**：ChatGPT（图）+ 1-2 家文本 + 搜索。加上 OCR 自建。

所以"1-2 家"的准确表述应该是：**2 家模型供应商（ChatGPT + 1 家文本）+ 1 家搜索 + 自建 OCR**。不是字面的"1-2 家"。

## 三、收敛方案（推荐）

### 文本链路：4 家 → 2 家

| 步骤 | 现有 | 收敛后 | 理由 |
|---|---|---|---|
| 正文生成 | 豆包 | 豆包（保留） | 已在用，快速模式成熟 |
| 校稿×2 | Kimi | Kimi 1 轮（合并两轮） | 两轮校稿可合并为一次"校稿+检查" |
| 检查 | DeepSeek | **砍掉** | 与 Kimi 校稿职责重叠 |
| 检查+生图提示词 | workbuddy | **砍掉 workbuddy** | 生图提示词复用豆包生成 |

收敛后文本调用：豆包生成（1）→ Kimi 校稿+检查（1）→ 豆包生图提示词（1）= 3 次/条。

### 图片链路：2 家保持

| 步骤 | 现有 | 收敛后 | 理由 |
|---|---|---|---|
| 搜实景图 | 豆包搜索 | 豆包搜索（保留） | 搜索 API，无替代压力 |
| 图片生成 | ChatGPT | ChatGPT（保留） | 独占，无法替换 |

### 最终模型组合

**2 家模型供应商 + 1 家搜索 + 自建 OCR**：
- 文本：豆包（生成 + 生图提示词）+ Kimi（校稿检查）
- 图片：ChatGPT（DALL-E）
- 搜索：豆包搜索
- OCR：PaddleOCR（自建）

## 四、替换/降级策略

| 任务 | 主供应商 | 备供应商 | 降级现实 |
|---|---|---|---|
| 正文生成 | 豆包 | DeepSeek | 文本可替换 ✓ |
| 校稿检查 | Kimi | 豆包 | 文本可替换 ✓ |
| 生图提示词 | 豆包 | DeepSeek | 文本可替换 ✓ |
| 图片生成 | ChatGPT | **无等价替代** | 只能重试 + 转人工 ✗ |
| 搜实景图 | 豆包搜索 | 换搜索 API | 可替换 ✓ |
| OCR | PaddleOCR | 第三方 OCR | 可替换 ✓ |

**核心结论**：图片生成的"主备切换"现实中不成立。ChatGPT 挂了没有备胎，降级路径只能是"重试 N 次 + 转人工（B 角色）"，不是"切备供应商"。

这与 spec §8.1 的写法有冲突：
- spec §8.1 把图片生成写成"允许 2 张图替换"（暗示有备选图源）
- 现实是"重试 + 转人工"，因为 3:4 中文竖版图只有 ChatGPT 能产

---

## 五、对 spec 的修订建议

1. **§1.1 修正**："模型供应商收敛到 1-2 家" → "模型供应商 2 家（ChatGPT 图片 + 豆包/DeepSeek/Kimi 文本选型）+ 1 家搜索 + 自建 OCR"
2. **§8.1 修正**：图片生成降级从"允许 2 张图替换" → "重试 3 次 + 转人工（B 角色必看）"，明确图片无备供应商
3. **V-C02 细化**：待确认项从"1-2 家名单" → 明确为"图片供应商固定 ChatGPT + 文本供应商选 1 家（豆包/DeepSeek/Kimi 三选一）+ 搜索供应商"

## 六、待确认（需客户/供应商数据）

本分析基于"现有 5 家"的定性判断，未纳入价格和并发额度。要定最终选型，还需：

1. 三家文本供应商（豆包/DeepSeek/Kimi）的单价对比（元/千 token）
2. ChatGPT 图片生成的单价（元/张）和并发额度
3. 豆包搜索 API 的单价和额度
4. 各家的 429 限流策略和 SLA

拿到这些数据后，才能从"定性收敛"到"定量选型"（单任务包成本 = Σ各步调用成本）。

## 七、最终选型决策（2026-08-14 客户确定）

客户已确定三点，本分析从"建议"转为"既成决策"：

### 7.1 确定的三点

| 步骤 | 决策 |
|---|---|
| 正文生成 | 豆包 → **DeepSeek 4 Pro** 替换 |
| 校稿检查 | **Kimi** 合并一轮（原两轮 → 一轮） |
| 图片生成 | **ChatGPT**，通过**单独机器转发调用** |

### 7.2 最终模型组合（完整闭环）

| 任务 | 模型 | 备注 |
|---|---|---|
| 正文生成 | DeepSeek 4 Pro | 替换豆包 |
| 生图提示词 | DeepSeek 4 Pro | 复用生成模型（豆包原职责转移） |
| 校稿检查 | Kimi K3 | 两轮合并一轮 |
| 证据包搜索 | 豆包搜索 API（网页） | 独立 key，≠ 方舟 key |
| 搜实景图（主） | 豆包大模型（方舟） | 专家模式多模态搜图，复刻手工业务 |
| 搜实景图（备） | DeepSeek 4 Pro + 百度搜索 | 备用降级 |
| 图片生成 | ChatGPT（DALL-E） | 单独机器转发（网络中转） |
| OCR | PaddleOCR（自建） | 不变 |

### 7.3 新增架构点：ChatGPT 转发机器

"单独机器转发调用"意味着部署架构多一个组件：一台独立机器专门转发 ChatGPT 调用。可能的动机（待客户确认具体原因）：

- **合规/出域控制**：ChatGPT（OpenAI）在境外，转发机器作为跳板，集中控制数据出域点
- **网络稳定**：国内直连 OpenAI 不稳定，中转机器保证调用稳定
- **API key 隔离 + 统一计费**：key 只存在转发机器上，验证平台不直接持有

对 spec 的影响：
- §18 最小部署方案需加"ChatGPT 转发机器"（与验证平台分离的一台机器）
- 转发机器的规格、网络、key 管理需在 V-C04 部署确认时一并明确

## 八、定量成本分析（基于确定选型 + 价格）

### 8.1 单条内容的模型成本（1 正文 + 6 图）

假设 token 用量：正文生成输入 ~500 / 输出 ~800；校稿输入 ~1500 / 输出 ~1000；生图提示词输入 ~1000 / 输出 ~500。

| 步骤 | 模型 | 成本（元/条） |
|---|---|---|
| 正文生成 | DeepSeek V4-Pro | 500×3/1M + 800×6/1M = 0.0063 |
| 校稿检查 | Kimi K3 | 1500×20/1M + 1000×100/1M = 0.13 |
| 生图提示词 | DeepSeek V4-Pro | 1000×3/1M + 500×6/1M = 0.006 |
| **文本小计** | | **≈0.142 元/条** |
| 图片生成 | ChatGPT（6 张） | 6 × $0.04×7.2 ≈ 1.73 元/条 |
| **总计** | | **≈1.87 元/条** |

### 8.2 月产 10 万条的成本

| 项 | 月成本 |
|---|---|
| 文本 | 10 万 × 0.142 ≈ 1.42 万/月 |
| 图片 | 10 万 × 1.73 ≈ 17.3 万/月 |
| **总计** | **≈18.7 万/月（模型成本，不含人工/存储/OCR）** |

### 8.3 三个关键结论

**结论 1：图片成本占模型总成本的 92%**（1.73 / 1.87）。图片是绝对约束，文本模型怎么选对总成本影响 <10%。

**结论 2：Kimi 校稿是文本成本的大头，但绝对值很小**。Kimi（输出 100 元/1M）比 DeepSeek（6 元/1M）贵 16 倍，校稿单步 0.13 元占文本成本 93%，但只占总成本 7%。即使校稿也换 DeepSeek，总成本只降 6%（1.87 → 1.75），省 0.12 元/条。

**结论 3：真正要优化的是图片单价，不是文本**。如果图片每张从 $0.04 降到 $0.02，总成本从 1.87 降到 1.0（降 46%）。图片的单价、并发额度、以及"是否每张都要最高质量"才是成本优化的主战场。

### 8.4 待补数据

- **图片每张价格**：上面用的 $0.04/张（DALL-E 3 1024×1024）是假设，需确认 ChatGPT 生图实际单价（gpt-image-1 按质量/尺寸计费，范围 $0.02-$0.12/张）
- **图片并发额度**：峰值 60 条/分钟 = 360 张/分钟，转发机器能否扛住，OpenAI 是否限流
- **缓存命中率**：DeepSeek/Kimi 的输入缓存命中率会影响成本（命中 0.025 vs 未命中 3，差 120 倍）

## 九、搜索接入（2026-08-14 确认）

### 9.1 两个搜索用途，两个 API

| 用途 | API | 状态 |
|---|---|---|
| 证据包构建（claims/evidence 事实来源） | 豆包搜索 API（网页搜索） | 已确认，接入方案如下 |
| 实景图素材（喂 ChatGPT 生图融合） | 图片搜索 API（必应/百度等） | **待定**，豆包网页搜索不含图 |

### 9.2 豆包搜索 API（Custom 国内网页版）接入要点

- **接口**：`POST https://search-infinity.volcengineapi.com/api/v1/custom_search`
- **鉴权**：`Authorization: Bearer SEARCH_API_KEY`（**独立 key ≠ 方舟模型 key，两套密钥分开**）
- **免费额度**：500 次/月，主账号维度，每月 1 号重置，优先扣免费
- **QPS**：默认 5，高并发需火山工单提 QPS
- **返回**：`Result.WebPageItems`（title/url/summary/publishTime）
- **两版本**：Custom（国内网页/新闻/公众号/抖音，中文好）vs Global（海外网页，`open.feedcoopapi.com/search_api/global_search`）
- **最佳实践**：只传 summary 摘要给大模型，不要把完整 HTML 塞进去（爆 token）

**QPS 约束提醒**：证据包构建若每条约 1-2 次搜索，峰值 60 条/分钟 = 120 次/分钟 = 2 次/秒，QPS=5 勉强够但接近上限，需在验证前确认是否要提工单扩容。

### 9.3 搜实景图（已确定，2026-08-14）

手工业务的搜图 = 豆包**大模型**（方舟）专家模式多模态联网搜图，不是独立搜索 API。

**最终方案**：

| 优先级 | 方案 | 说明 |
|---|---|---|
| 主 | 豆包大模型（方舟）专家模式 | 复刻手工业务，多模态联网搜真实图片 |
| 备 | DeepSeek 4 Pro + 百度搜索 | 降级方案，DeepSeek 负责解析 + 百度搜图 |

**注意**：豆包大模型（方舟）与豆包搜索 API（网页）是两个不同产品、不同 key、不同接口，需分别开通。方舟 key 用于搜实景图（多模态），搜索 API key 用于证据包（网页文本）。
