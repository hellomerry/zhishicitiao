## 1. 总目标与核心方法

**目标**：从 0 到月产 10 万条"图文内容"（1 篇正文 + 6 张图 / 条），并给出可复制的产能模型。

**核心方法**：先建"产能计量仪器"（验证平台），用真实数据测出稳定合格产能，再据此推算人员、算力、成本，最后规模化。**不凭拍脑袋定人员编制和服务器规模。**

**关键口径**：
- 一条 = 1 篇正文（400-700 字）+ 6 张图（1 封面 + 5 内页），不含发布
- 抽检比例 20%（固定机制，不作为变量）
- 风险分流：绿 85% / 黄 10% / 红 3%（试运行实测校准）

**一条硬结论（决定路线）**：如果每条内容三人逐条审核，3-12 人无法达标。产能瓶颈在**绿色比例与抽检比例**，不在生成速度。

## 10. 队列 / 流式 / 抽查增强（2026-08-15）

> 客户反馈驱动的增量需求，落在轻量栈原型（S0/S1）上。

### 10.1 需求来源（客户原话要点）

1. Query 导入后工作需**排队**（因为部分大模型有并发限制）
2. 系统应能**通过测试动态调整工作频率**（自适应并发，不靠人工拍）
3. **流式输出**看到工作进度，像《黑客帝国》屏幕一样——有画面执行效果 + 实际内容
4. 自动输出的内容允许**随机抽查**

### 10.2 设计决策

| 项 | 决策 |
|---|---|
| 队列模型 | 进程内 `asyncio.Queue` + 固定 worker 池（`max_concurrency` 个协程），自适应信号量控制并发 |
| 自适应算法 | AIMD：限流(429/rate limit)→并发**减半**；连续成功满周期→并发 **+1**；连续普通失败≥3→并发 **-1** |
| 流式传输 | SSE（Server-Sent Events，单向推送），前端 `EventSource` 订阅 |
| 事件总线 | 进程内 pub/sub（每订阅者一个 `asyncio.Queue`）；单进程 uvicorn 足够，多 worker 需换 Redis pub/sub |
| 进度可视化 | 全屏 Matrix 绿字雨 canvas + 半透明实时任务卡片（正文预览 / 配图缩略图 / 风险分流 / 节点进度） |
| 随机抽查 | `GET /api/tasks/random_sample` 随机取一条 `review`/`approved`，返回正文 + 6 图 + 证据 + 风险 |
| 重启恢复 | 调度器启动时把 `draft`/`processing` 状态任务重新入队，队列具备重启韧性 |

### 10.3 新增 / 改动文件

- 新增 `src/stream/bus.py`：事件总线（进程内 pub/sub）
- 新增 `src/stream/limiter.py`：自适应并发限制器（AIMD）
- 新增 `src/stream/scheduler.py`：队列 + worker 池 + 限流识别 + 重启恢复
- 新增 `src/api/stream.py`：`/api/stream/events`（SSE）+ `/api/stream/state`（快照）
- 新增 `static/stream.html`：Matrix 流式监控页
- 新增 `static/sample.html`：随机抽查页
- 改动 `src/api/tasks.py`：`import_queries` 改入队（不再扇出），新增 `random_sample`
- 改动 `src/pipeline/nodes.py`：节点事件埋点（node_started/finished/failed）+ `asset_gen` 返回 `image_urls`
- 改动 `src/config.py`：新增 `initial/min/max_concurrency`
- 改动 `src/api/main.py`：注册流式路由 + lifespan 启动/停止调度器 + `/stream`、`/sample` 页面路由
- 改动 `static/common.js`：侧边栏新增「流式监控」「随机抽查」菜单

### 10.4 验证结果（2026-08-15 实测）

- 导入 3 条 Query → 2 并发 + 1 排队 ✓
- SSE 实时推送 `task_enqueued/started` + `node_started/finished` + 实际内容（搜图 6 / 证据 6 / 正文生成）✓
- 任务完成后状态 `review`，随机抽查返回真实正文（DeepSeek）+ 官方搜图 + AI 生成图 ✓

## 11. 后台管理 / 工作周期（2026-08-15）

> 客户反馈：需要后台管理，每 23 小时重置当前工作、手动检修、停机 1 小时；停机期间可导出工作记录、删除工作内容、重新开启工作任务。

### 11.1 设计决策

| 项 | 决策 |
|---|---|
| 工作周期 | `CycleManager`：工作 `work_hours`(23h) → 检修停机 `maintenance_hours`(1h) → 循环，后台每 5s 轮询自动切换 |
| 停机语义 | 停机 = 调度器 `pause()`（停止取新任务，已在跑的任务继续完成） |
| 手动检修 | `POST /api/admin/maintenance/start` 立即进入停机（幂等） |
| 重新开启 | `POST /api/admin/restart` 结束停机、恢复调度、开启新周期 |
| 导出记录 | `GET /api/admin/export` 导出 CSV（任务/正文长度/图/证据/成本/风险），中文文件名用 RFC 5987 编码 |
| 删除内容 | `POST /api/admin/clear` 清空 19 张工作表（保留 users/organizations），`lock_timeout=10s` 防挂起 |
| 周期持久化 | 进程内状态，重启后从工作态重新计时（后续可落库持久化） |

### 11.2 新增 / 改动文件

- 新增 `src/stream/maintenance.py`：`CycleManager`（23h/1h 循环 + 暂停/恢复调度器）
- 新增 `src/api/admin.py`：状态 / 检修 / 重启 / 导出 / 删除接口
- 新增 `static/admin.html`：后台管理页（周期倒计时 + 运维按钮）
- 改动 `src/stream/scheduler.py`：`pause()` / `resume()` / `clear()` + worker 暂停闸门 + 失败时更新 DB 状态
- 改动 `src/config.py`：`work_hours` / `maintenance_hours`
- 改动 `src/api/main.py`：注册 admin 路由 + lifespan 启动 cycle + `/admin` 页面路由
- 改动 `static/common.js`：侧边栏新增「后台管理」菜单

### 11.3 验证结果（2026-08-15 实测）

- 工作周期倒计时 23h / 检修 1h ✓
- 手动检修 → 调度器暂停（检修中再导入的任务保持排队）✓
- 导出 CSV（中文文件名 + 任务数据）✓
- 删除内容：有在跑任务时快速返回错误（lock_timeout），空闲时清空 19 表 ✓
- 重新开启 → 恢复调度、新周期计时 ✓
- 前端 `/admin` 正常加载 ✓
- 修复回归 bug：任务失败时 DB 状态由卡 `processing` 改为正确写 `failed` ✓
- 34 测试全通过 ✓
