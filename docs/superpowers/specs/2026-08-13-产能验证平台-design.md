## 0. 文档定位

本文不是生产平台 PRD，而是**产能验证平台的设计文档**。目的是建一台可信赖的"产能计量仪器"，用 3 人 + 验证平台跑出真实数据，回答月产 10 万条需要多少人、什么岗位、多少模型算力、什么成本。

文档不替代正式 PRD 和架构设计；当验证结束、产能数据定下来后，再进入生产平台详细设计。

## 1. 背景与前提

### 1.1 既有决策（来自 brainstorming 澄清）

| 项 | 决定 |
|---|---|
| 验证方法 | 三阶段递进：1 人跑通流程 → 3 人协作验证 → 6 人实测目标配置 |
| 验证目标 | Q3（3人）稳定合格产能 ≥ 2,840 条/天 → 反推需 6 人；Q6（6人）稳定合格产能 ≥ 4,545 条/天 → 覆盖月产 10 万条 |
| 一条口径 | 1 篇正文（400-700 字）+ 6 张图（1 封面 + 5 内页），不含发布 |
| 批次会签 | 平台内建为固定机制 |
| 抽检比例 | 20% |
| 模型供应商 | 收敛到 1-2 家（具体供应商在合同/合规确认后定） |
| 部署 | 客户本地 |
| 技术栈 | 复用 Temporal + FastAPI + PostgreSQL + Redis |
| 总体方案 | 两段式：第一段轻量栈跑流程调通，第二段迁 Temporal 跑小批与稳定性 |
| 6 人配置张力 | 直接测，不再外推；6 人阶段实测结果即结论 |
| 本地部署张力 | 仅指验证平台；模型 API 仍走公网，由 IT/法务独立确认（REQ-C06） |

### 1.2 来自需求文档的未闭环项（本文明确处理）

- REQ-C01（一条口径）：已闭环为"任务包 = 1 正 + 6 图"
- REQ-C02（批次会签 + 抽检）：已闭环为"内建 + 20% 抽检"
- REQ-C05（发布平台）：不在验证范围（不含发布）
- REQ-C06（部署与第三方模型）：本地部署验证平台 + 模型 API 出域由 IT/法务另行确认
- REQ-C07（素材版权/示意属性）：纳入验证范围，使用现有 docx 案例中已使用的素材类别（官方实景 + AI 示意）
- REQ-C08（业务 SLA）：验证期 SLA 暂定为 24 小时/任务包，不承诺紧急任务

未闭环项（不在本文处理）：REQ-C03（责任人名单）、REQ-C04（高风险白名单）、REQ-C05（发布平台接口）。

### 1.3 反推与张力

- 6 人配置：每人/天 ~473 条任务包 × 人工触达率 33% = 每人/天 ~156 条逐条审。每条 3 分钟踩在专业域结构化问题单的极限边缘。**6 人阶段直接实测**，结果即结论；如果产能不足，回到 9-12 人配置（不是平台失败）。
- 单人阶段：1 人同时扮演 A/B/C 三个角色，无并行。需要工作台支持"角色切换"或"三队列全可见"，否则单人无法完成端到端流程。
- 模型 API 必然出域：本地部署只解决验证平台本身不出客户内网，模型调用仍走公网。验证开始前由客户 IT/法务独立确认。
- Temporal 启动代价：1-2 周才能跑通第一条。本方案用"两段式"吸收，第一段先上轻量栈。

## 2. 验证目标

### 2.1 四个核心问题

1. 3 人每天能完成多少条合格内容（稳定合格产能）？
2. 人工时间主要消耗在哪些审核环节？
3. 文本生成、图片生成、OCR 和质检需要多少算力及调用成本？
4. 扩展到月产 10 万条时，需要多少人员、模型并发和机器资源？

### 2.2 产能口径

> 一条合格内容 = 正文完成 + 6 张图完成 + 机器检查通过 + 三个责任域审核完成 + 问题关闭 + 形成可交付版本。

不含发布操作。

**"三个责任域审核完成"的明确口径（工程评审澄清）**：绿色内容通过"机器门禁 + 批次会签"视为审核完成（未抽检的绿色不逐条人工审，抽中的 20% 才人工审）；黄色逐条进对应专业队列人工审；红色 A/B/C 三队列 + 合规会签。即"审核完成"不等于"人工逐条三域审"，而是"该内容走了它风险等级对应的完整审核路径"。

### 2.3 三类产能指标

- **极限产能**：短时间全速运行的最高数量
- **稳定产能**：连续工作多日、质量达标情况下的日均数量
- **合格产能**：扣除返工、驳回、不合格内容后的有效交付数量

**真正用于推算 10 万条规模的，是"稳定合格产能"。**

### 2.4 人力推算公式

```
Q3 = 3 人每天完成的合格内容数量
D  = 每月有效生产天数（按 22）
S  = 规模扩大后的效率系数（0.75-0.85）

理论人员数 = 3 × 100,000 ÷ (Q3 × 22)
建议人员数 = 理论人员数 ÷ S
```

### 2.5 算力与模型资源测算

验证平台为每条任务记录：

```
月文本调用量 = 单条平均文本调用次数 × 100,000
月图片调用量 = 单条平均图片生成次数 × 100,000
月 OCR 调用量 = 6 × 100,000 = 600,000
月存储量    = 单条平均文件大小 × 100,000
月模型成本  = 单条平均模型成本 × 100,000
```

### 2.6 峰值与并发

月产 10 万 ÷ 22 工作日 ÷ 8 小时 = 平均 ~9.5 条/分钟。验证平台需至少达到：

- **10 条/分钟** 持续处理
- **20-30 条/分钟** 短时峰值
- **20-30% 重试余量**
- 文本/图片/OCR 供应商限流表现
- 外部模型不可用时的队列积压及恢复速度

## 3. 团队配置与责任域

### 3.1 责任域（始终是三个，不随团队规模变）

| 人员 | 主要职责 | 验证重点 |
|---|---|---|
| A：文案与事实审核 | 正文、事实、数据、实体、时效、真实性 | 单条审核时间、事实问题率 |
| B：图片与版权审核 | 图片主体、版权、清晰度、版式、图文一致性 | 图片审核时间、返工率 |
| C：合规与交付审核 | 平台规范、风险、问题闭环、会签、交付 | 最终签发时间、拦截率 |

### 3.2 三阶段团队配置

| 阶段 | 人数 | 角色分配 | 工作台要求 |
|---|---|---|---|
| 单人阶段 | 1 人 | 同一人顺序扮演 A → B → C | 三队列全部可见；支持角色切换；记录"角色切换次数"作为流程摩擦指标 |
| 三人阶段 | 3 人 | A、B、C 各 1 人（并行） | 三角色独立队列，与正式生产一致 |
| 六人阶段 | 6 人 | A、B、C 各 2 人（含主审+复核） | 多人复核、会签、跨人接管场景 |

**单人阶段目的**：验证"一个人穿三顶帽子能否走通端到端"，不是测产能；产出每专业域单人操作基线时长（用于三/六人阶段对比）。

### 3.3 权限与职责隔离

- 内容生产者不能签署自己制作内容的事实审核
- 图片生产者不能签署自己制作图片的版权审核
- P0 问题的处理人不能作为唯一复核人
- 管理员强制放行必须填写理由并进入审计报告

验证期不引入额外管理员；强制放行通过 C 角色兼任 + 审计日志实现。

## 4. 平台架构

### 4.1 两段式栈

| 段 | 时间窗 | 栈 | 目的 |
|---|---|---|---|
| 第一段（流程调通） | 约 2 周 | FastAPI + asyncio + Redis Streams + PostgreSQL | 跑通 50-100 条，验证口径、埋点、看板，采集首批真实时间数据 |
| 第二段（小批+压力+稳定性） | 约 4-5 周 | 迁到 Temporal + FastAPI + PostgreSQL + Redis Streams + LiteLLM Adapter | 跑 300-5,000 条，得出可外推到 10 万条/月的可信产能数据 |

### 4.2 关键约束

- PG Schema 从第一段开始就按"两套栈都可用"设计
- 所有状态字段、版本号、幂等键、签字表都按 Temporal Activity 可直接读写来建
- 第二段只换编排层，不动数据层
- 跨阶段数据对账：第二段跑同样 100 条，对比两套栈的耗时差异，< 15% 视为栈迁移不影响数据可信

### 4.3 模块边界（8 个）

1. **任务导入**：Excel/CSV 导入 Query，生成任务 ID + 幂等键
2. **实体与证据库**：学校/产品/政策版本化的实体快照，证据包
3. **流水线编排**：第一段 asyncio，第二段 Temporal Workflow
4. **模型网关**：LiteLLM + 自研 Adapter，路由文本/搜索/图片/OCR，1-2 家供应商
5. **质检引擎**：字数、标题、绝对化词、免责声明、OCR 关键字段比对、图文一致性
6. **审核工作台**：三角色独立队列，结构化问题单，签字与签发
7. **看板与埋点**：每条任务、每节点、每审核动作的时间戳与耗时
8. **批次会签**：固定机制，绿色 85% 走批次 + 20% 抽检

### 4.4 与生产平台的关系

验证平台是**临时性产物**。结束后交付物是产能报告 + 真实参数集，不是平台代码本身。PG Schema 和 LiteLLM Adapter 可以直接复用到生产平台。

## 5. 数据流与生命周期

### 5.1 任务生命周期

```
[Excel/CSV]
   ↓
① 任务导入          → tasks（幂等键 + Query + 类型 + SLA）
   ↓
② 实体绑定          → entity_snapshots（学校/SKU/政策版本 + 有效期）
   ↓
③ 证据包构建         → claims + evidence（事实点 ID、来源等级、URL、日期）
   ↓
④ 正文生成           → drafts（主稿版本、提示词版本、模型版本、token、耗时）
   ↓
⑤ 规则质检           → rule_results（字数/标题/绝对化/免责，失败不入绿）
   ↓
⑥ 分页文案生成        → page_copies（每页 fact_id 引用、字数）
   ↓
⑦ 图片生成           → assets（主体、来源、版权、哈希、模型版本、耗时）
   ↓
⑧ OCR 回读           → ocr_results（关键字段、置信度）
   ↓
⑨ 图文一致性          → cross_checks（OCR vs page_copy 事实 ID）
   ↓
⑩ 风险分流           → risk_classifications（绿/黄/红，依据 = 上面所有结果）
   ↓
⑪ 三方审核队列        → review_sessions（角色、独占锁、开始/结束时间戳）
   ↓
⑫ 批次会签           → batches + approvals（成员清单、抽样、签字）
   ↓
⑬ 发布快照           → publish_snapshots（不可变：正文+图片+规则+模型+签字）
   ↓
[看板埋点聚合]
```

### 5.2 埋点统一约定：node_events 表

每个节点都产出三段时间戳到统一的 `node_events` 表：

| 字段 | 含义 | 谁写 |
|---|---|---|
| `enqueued_at` | 节点被加入队列 | 编排器 |
| `started_at` | 节点实际开始执行 | Activity |
| `finished_at` | 节点完成（成功/失败） | Activity |

附加字段：`model_version`、`prompt_version`、`retry_count`、`cost_estimate_cny`、`error_class`。

看板所有指标都能从这张表 + `review_sessions` 实时聚合得出。

### 5.3 幂等键设计

- `task_id`：导入时生成（UUID）
- `node_idempotency_key`：每节点的 `(task_id, node_name, node_input_hash)`，重跑同一节点不会重复计费或写脏
- `review_action_idempotency_key`：审核动作的 `(review_session_id, action_type, payload_hash)`，防止双击

### 5.4 风险分流触发条件

| 等级 | 触发 | 后续 |
|---|---|---|
| 🟢 绿 | 所有机器门禁通过 + 无来源冲突 + OCR 关键字段 100% 一致 + 图文一致 | 进批次，20% 抽样进 A/B/C 单域审核 |
| 🟡 黄 | 任一规则失败 / 单项低置信度 / 单一专业域问题 | 进对应专业队列（A/B/C），逐条 |
| 🔴 红 | P0 问题 / 多域冲突 / 版权不明 / 重大事实错误 | A+B+C 三队列 + 合规会签 |

## 6. 计量与时间采集

### 6.1 问题

审核员会切标签页、会同时开多条、会被打断、会忘记点完成。如果用 `finished_at - started_at`，测出来的每条耗时会被闲置时间污染，最终推到 10 万条/月偏差 30% 以上。

### 6.2 第一层：审核工作台前端

| 机制 | 作用 | 实现 |
|---|---|---|
| 活跃度心跳 | 区分"在操作"vs"挂起" | 每 10 秒前端 POST `/heartbeat`，30 秒无心跳即挂起；挂起期间不计入实际操作时间 |
| 单条独占锁 | 强制一条一审，禁止并行 | 进入审核页即锁，关闭/超时才释放；同任务不可被另一人领取 |
| 超时自动挂起 | 避免忘记点完成 | 连续 90 分钟无心跳自动挂起并写入 `auto_suspended_at` |
| 关键动作埋点 | 区分操作 vs 浏览 | `view_started_at` / `view_ended_at`，按组件（证据卡、OCR 比对卡、图册）分桶 |
| 审核动作原子化 | 每个动作都是一条事件 | 通过/驳回/转交/升级，每个动作写一行 `review_actions`，含 `client_ts` + `server_ts` |

### 6.3 第二层：后端对账

| 检查 | 频率 | 触发动作 |
|---|---|---|
| 客户端时钟漂移检测 | 每次心跳 | NTP 校准，>2 分钟偏差即报警并暂停该审核员的采集 |
| 异常值剔除规则 | 每小时聚合 | 单条耗时 < 5 秒或 > 60 分钟自动标记 `anomaly_flag`，不计入 P50/P95 |
| 前后端时间一致性 | 每条任务完成时 | `finished_at - started_at` 与 `sum(view_durations)` 偏差 > 30% 即标记 `time_inconsistency_flag` |
| 抽检样本人工对账 | 每天 5% | C 角色从已完成任务中抽 5%，逐条比对实际耗时与系统记录 |
| 双盲抽样对账 | 每周 | 第三方（非 A/B/C）按 10 条样本独立测一遍 |

### 6.4 反算公式

```
人均实际操作分钟/天 = Σ(single_action_durations) ÷ Σ(unique_reviewer_days)
人均逐条触达 = 当天实际触达条数 ÷ 当天登录天数
人均审核速度 = 人均实际操作分钟/天 ÷ 人均逐条触达  ← 单位：分钟/条
```

### 6.5 仪器精度报告（每周）

- `time_inconsistency_flag` 占比（理想 < 1%）
- 客户端时钟偏差分布
- 抽检对账偏差（理想 < 5%）
- 异常值剔除率（理想 3-8%）

### 6.6 精度不够的处理路径

- `time_inconsistency_flag` > 5%：先排查网络延迟或审核员操作模式，不调阈值
- 抽检对账偏差 > 10%：暂停产能采集，回到流程调通阶段补埋点

## 7. 看板指标

全部从 `node_events` + `review_sessions` + `batches` 实时聚合：

- **吞吐**：每小时创建/完成/合格交付数
- **首过率**：进入绿色且无抽检命中问题的占比
- **人工触达率**：进入人工队列的占比（绿抽 20% + 黄 100% + 红 100%）
- **返工率**：至少一次驳回的任务占比
- **P50 / P95 用时**：每节点 + 每审核环节
- **模型成本**：每任务包、每正文、每图片、每 OCR 的 CNY
- **队列积压**：每专业域的 pending 数
- **失败类型 Top-N**：按 `error_class` 聚合

## 8. 错误处理与降级

### 8.1 模型供应商降级链

| 场景 | 触发 | 动作 | 看板指标 |
|---|---|---|---|
| 主供应商超时 (>30s) | 单次调用超时 | 切备供应商，记录 `degraded=true` | `model_failover_rate` |
| 主供应商限流 (429) | API 返回 429 | 切备 + 退避 60s 重试主供应商 | `model_429_count` |
| 主备全挂 | 两次 failover 都失败 | 进延迟队列，30s 后重试，3 次失败转人工 | `dlq_depth` |
| 图片生成失败 | 同上，但单任务允许 2 张图替换 | 用图库已有素材替换 + 标记 `image_substituted` | `image_substitution_rate` |
| OCR 失败 | 置信度 < 阈值或服务挂 | 该张图转人工审核（B 角色必看） | `ocr_failure_rate` |

**关键原则**：降级不能伪造成功。任何降级路径都必须留下 `degraded=true` 和原始失败信息。

### 8.2 基础设施故障

| 故障 | 检测 | 恢复 | 数据保护 |
|---|---|---|---|
| PostgreSQL 挂 | 健康检查 + 心跳 | 30s 内重启；超过 5 分钟告警 | WAL 归档到本地盘 + 每日备份到客户指定存储 |
| Redis 挂 | 健康检查 | 60s 内重启；流任务回到 PG `outbox` 表重放 | Redis 数据全量可从 PG 重建 |
| 工作流引擎挂（第二段 Temporal） | namespace 心跳 | worker 5 分钟内自动重启 | Temporal 状态由 PG 后端持久化 |
| 模型供应商账号额度耗尽 | API 返回 quota 错误 | 自动切备 + 告警 + 暂停接新任务 | 不静默吞掉 |
| 本地磁盘满 | 容量监控 | 暂停接新任务 + 告警 | 旧任务产物按 30 天滚动归档 |

## 9. 测试策略

### 9.1 层 1：业务功能正确性

- 流水线端到端：50-100 条（流程调通阶段）
- 三角色审核闭环：覆盖绿/黄/红各 10 条
- 批次会签：同模板同规则批次 50 条，抽检 20% 触发
- OCR 关键字段不一致必驳回：人工注入 5 条错误样本
- 缺页/错序/两图同页必驳回：人工注入 5 条错误样本

### 9.2 层 2：计量精度正确性

- 埋点自检：每条任务的 `node_events` 时间线能重建完整生命周期
- 时钟漂移测试：故意把一台审核机时钟拨快/拨慢 3 分钟，验证告警触发
- 抽检对账：每天 5% 人工复核实际耗时 vs 系统记录
- 双盲对账：每周第三方独立测 10 条
- 异常值剔除验证：注入已知异常（5 秒完成、60 分钟完成），验证规则正确剔除
- 独占锁测试：同任务被两个人领取时，第二个必须失败

### 9.3 层 3：容量正确性

- 单日压力测试：3 人全速跑 8 小时，测极限
- 连续 3-5 天稳定性测试：取中位数作为稳定合格产能
- 峰值并发：60 条/分钟持续 5 分钟，测队列与降级
- 失败重试余量：注入 20% 失败率，验证重试后产能仍达标
- 跨阶段数据对账：第二段切到 Temporal 后跑同样 100 条，对比耗时差异 < 15%

## 10. 验证周期（三阶段递进）

### 10.1 阶段 0：单人跑通流程（1 人 × 约 1 周）

| 项 | 内容 |
|---|---|
| 规模 | 30-50 条（够覆盖三类内容类型 + 触发一次红/黄/绿即可） |
| 团队 | 1 人顺序扮演 A → B → C |
| 目的 | 验证流程可走通、机器门禁阈值合理、看板与埋点可用 |
| 关键产出 | 每专业域单人基线时长（用于三/六人阶段对比） |
| 退出条件 | 端到端流程走通、无系统级阻塞、单人可完成会签 |

### 10.2 阶段 1：三人协作验证（3 人 × 约 2 周）

| 项 | 内容 |
|---|---|
| 规模 | 流程调通 50-100 条 → 小批验证 300-500 条 |
| 团队 | A、B、C 各 1 人，并行 |
| 目的 | 验证角色分离后的协作、单条审核时间、事实问题率、返工率 |
| 关键产出 | 三角色并行下的真实产能；角色切换成本 vs 单人基线 |
| 退出条件 | 三角色队列无持续积压；P95 用时进入稳定区间 |

### 10.3 阶段 2：三人压力与稳定性（3 人 × 约 1-2 周）

| 项 | 内容 |
|---|---|
| 规模 | 单日压力测试（3 人全速 8 小时）+ 连续 3-5 天稳定性 |
| 团队 | 3 人同上 |
| 目的 | 测三人极限与稳定产能，得出 Q3（3 人稳定合格产能/天） |
| 关键产出 | Q3、模型成本、失败类型分布 |
| 退出条件 | 连续 3-5 天产能波动 < 5% |

### 10.4 阶段 3：六人实测目标配置（6 人 × 约 2-3 周）

| 项 | 内容 |
|---|---|
| 规模 | 流程调通（6 人版本）→ 小批验证 → 连续 3-5 天稳定性 |
| 团队 | A、B、C 各 2 人（主审 + 复核） |
| 目的 | **直接实测 6 人配置**，得出 Q6；对比 Q3 → Q6 的非线性收益 |
| 关键产出 | Q6（6 人稳定合格产能/天）；3 人→6 人边际收益曲线；6 人配置结论（达标/不足需扩到 9-12 人） |
| 退出条件 | 6 人连续 3-5 天稳定合格产能已采集；Q6 ≥ 4,545 条/天（覆盖月产 10 万）或 明确结论：需扩到 9-12 人 |

### 10.5 阶段间的数据衔接

| 阶段 | 上游依赖 | 衔接产物 |
|---|---|---|
| 0 → 1 | 单人跑通 + 单人基线时长 | 用于三人阶段对比"角色分离的协作增益" |
| 1 → 2 | 协作流程稳定 | 用于压力测试基线 |
| 2 → 3 | Q3 与机器门禁阈值 | 用于 6 人阶段预估（Q3 → Q6 推算区间） |

**关键原则**：第一天通常包含学习和流程磨合，不作为正式测算依据。每个阶段都使用连续 3-5 天的中位数或较保守的平均值。

### 10.6 停止条件（go/no-go 门槛，工程评审新增）

每个阶段结束设 go/no-go 判定，任一触发即暂停并转向（先解决模型/流程质量，再回来测产能），而不是继续后续阶段：

| 阶段 | 停止触发条件（任一） |
|---|---|
| 阶段 0（单人跑通） | 端到端流程无法走通；或模型产出无法达到基本可读（正文不成文、图片不可用） |
| 阶段 1（三人协作） | 绿色比例 < 40%；或单条人工耗时中位数 > 15 分钟；或重大事实错误率 > 1% |
| 阶段 2（三人压力） | 连续 3-5 天产能持续下降（无稳定）；或队列持续增长无法收敛 |
| 阶段 3（六人实测） | 6 人产能 < 4,545 条/天 且 边际收益显著递减（Q6/Q3 < 1.5 倍） |

触发停止后：输出已采集的真实数据 + 原因分析，由项目方决策是"优化模型/流程后重跑"还是"调整内容形态/目标"。停止不是失败，是 fail-fast——避免在质量不可行时继续烧 Temporal 迁移和六人实测的成本。

## 11. 达标标准

不能只看一天生产了多少条。需同时满足：

- 合格内容产量达到预设目标
- 首次通过率达到约 85%
- 重大事实错误为零
- 关键图文一致性达到 99.9% 以上
- 人工平均处理时间进入稳定区间
- 队列不会持续增长
- 返工率和失败率在可接受范围内
- 单条综合成本满足预算
- 连续 3-5 天没有明显产能下降

数量达标但质量下降、返工积压或人员明显超负荷，**不视为通过**。
